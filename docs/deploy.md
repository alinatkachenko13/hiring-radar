# Развёртывание на VPS

Ежедневный прогон должен идти без участия ноутбука. Сервер — единственное место,
где пайплайн работает постоянно: Airflow, Postgres и задания пайплайна живут в
контейнерах, сырьё лежит на диске сервера, витрины собираются в BigQuery.

Код на сервер приезжает из GitHub. Секреты в репозитории не хранятся и
копируются отдельно: `.env` и ключ сервисного аккаунта GCP.

## Что нужно от сервера

| Параметр | Значение | Почему |
|---|---|---|
| ОС | Ubuntu 24.04 LTS | под неё написаны команды ниже |
| Память | 4 ГБ | Airflow и Postgres вместе занимают около 2 ГБ |
| Процессор | 2 ядра | сбор упирается не в процессор, а в ожидание ответов API |
| Диск | 40 ГБ | сырьё растёт примерно на 35 МБ в день, это около 1 ГБ в месяц |

Подойдёт любой провайдер: Hetzner CX22, DigitalOcean, Contabo. Порядка €5 в месяц.

Часовой пояс сервера значения не имеет: DAG запускается в 06:00 UTC.

## Установка

Всё выполняется на сервере, под пользователем с правом `sudo`.

```bash
sudo apt update && sudo apt install -y ca-certificates curl git
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
```

После `usermod` нужно перезайти по SSH, иначе `docker` попросит `sudo`.

```bash
git clone https://github.com/alinatkachenko13/hiring-radar.git
cd hiring-radar
```

## Секреты

Эти два файла в git не попадают, поэтому копируются с ноутбука. Команды
выполняются **на ноутбуке**, из папки проекта:

```bash
scp .env <пользователь>@<адрес сервера>:~/hiring-radar/.env
scp gcp-service-account.json <пользователь>@<адрес сервера>:~/hiring-radar/gcp-service-account.json
```

В `.env` на сервере должны быть заполнены: ключи Adzuna, `GCP_PROJECT`,
`GCP_LOCATION`, `GOOGLE_APPLICATION_CREDENTIALS`, а также `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID`, иначе о сбоях никто не узнает.

## Настройки под конкретный сервер

Имя проекта, порт, лимит памяти и uid вынесены в переменные, потому что на общем
сервере значения по умолчанию не годятся. Дописываются в `.env` на сервере:

```bash
COMPOSE_PROJECT_NAME=alina-hiring-radar
AIRFLOW_PORT=9010
AIRFLOW_MEM_LIMIT=1500m
AIRFLOW_UID=1001
```

Зачем каждая:

- **имя проекта** — контейнеры не должны столкнуться именами с чужими;
- **порт** — 8080 на общем сервере занимает CI, свободные порты начинаются с 9000.
  Публикуется он только на localhost: запись вида `"9010:8080"` обходит фаервол и
  открывает Airflow всему интернету;
- **память** — Airflow занимает около 1 ГБ, и без лимита при нехватке памяти ядро
  убьёт не его, а самый крупный процесс на машине, возможно чужой;
- **uid** — контейнер пишет в `data/raw` через смонтированную папку, и файлы
  должны принадлежать владельцу каталога. Узнать свой: `id -u`.

## Сырьё за прошлые дни

Не обязательно: склад собирается из того, что есть, а история накопится заново.
Если прошлые дни нужны, копируются они так (команда на ноутбуке):

```bash
rsync -av data/raw/ <пользователь>@<адрес сервера>:~/hiring-radar/data/raw/
```

## Запуск

```bash
docker compose up -d --build
docker compose ps
```

Первая сборка занимает несколько минут: скачивается образ Airflow и ставятся
зависимости пайплайна. Дальше DAG `hiring_radar_daily` запускается сам каждый
день в 06:00 UTC. После первого запуска его нужно один раз снять с паузы:

```bash
docker compose exec airflow airflow dags unpause hiring_radar_daily
```

## Интерфейс Airflow

Порт 8080 слушает только localhost сервера, наружу он не открыт. Туннель
поднимается с ноутбука:

```bash
ssh -L 9010:localhost:9010 <пользователь>@<адрес сервера>
```

Пока сессия открыта, интерфейс доступен на http://localhost:9010. Логин `admin`,
пароль Airflow сгенерировал при первом запуске:

```bash
docker compose exec airflow cat /opt/airflow/simple_auth_manager_passwords.json.generated
```

Открывать порт 8080 наружу не нужно: у Airflow есть доступ и к ключам, и к складу.

## Обновление кода

```bash
cd ~/hiring-radar && git pull && docker compose up -d --build
```

Пересборка образа нужна только при изменении `requirements.txt`, но лишней не
бывает: контейнер поднимается заново за секунды, а код и так смонтирован с диска.

## Проверка, что всё живо

```bash
docker compose ps                      # оба контейнера Up, postgres healthy
curl -s localhost:9010/api/v2/monitor/health
docker compose exec airflow airflow dags list-runs hiring_radar_daily
ls data/raw | tail -3                  # файлы за сегодняшнюю дату
```

Лучшая проверка — алерт в Telegram: сломайте что-нибудь намеренно (например,
уберите ключ Adzuna из `.env`) и убедитесь, что сообщение пришло.

## Что помнить про диск

Сырьё не удаляется никогда: это неизменяемый слой, из которого пересобирается всё
остальное. Но растёт оно ощутимо — перепись даёт около 50 МБ в день.

Чтобы диск не заполнялся, за этим следят две вещи, обе работают сами:

- последняя задача DAG, `compress`, сжимает файлы старше 14 дней (`compress_raw.py`).
  Читатели разницы не замечают: сжатые и обычные файлы одинаково открывает
  `raw_files.py`;
- `load.py` после успешной загрузки удаляет промежуточные jsonl. Это копия сырья
  в другом формате, она весит столько же и после загрузки не нужна. Оставить их
  для отладки: `--keep-temp`.

Локальный склад DuckDB на сервере не создаётся: в DAG загрузка идёт с
`--backend bigquery`.

Если когда-нибудь и этого станет мало, следующий шаг — переносить старое сырьё в
объектное хранилище GCS. Это снимает зависимость от диска одного сервера, но
требует правок в `extract.py` и `load.py`.
